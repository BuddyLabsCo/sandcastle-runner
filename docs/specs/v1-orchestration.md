# Sandcastle Runner V1: ticket delivery orchestration

## Problem Statement

A developer delivering a Parent Ticket through several child tickets must repeatedly select unblocked work, isolate concurrent changes, supervise coding agents, publish pull requests, repair CI and conflicts, integrate changes, verify ticket closure, and maintain project documentation. Manual coordination makes it easy to start blocked work, mistake an agent's completion claim for delivery, merge a Batch prematurely, or lose track of unfinished work.

The developer needs a configurable local CLI that owns this orchestration deterministically while delegating coding to a selected native Sandcastle agent. Its full behavior must be verifiable without running real agents or modifying live services. V1 deliberately depends on a present, trusted operator for execution failures and has no daemon. It persists a Recovery Snapshot for restart resumption from exact delivery evidence, but it adds no durable agent-conversation recovery.

## Solution

An operator selects one configured Project and one Parent Ticket for a Run. The Runner discovers eligible direct children, reserves up to the Project-configured maximum number of Delivery Tickets, prepares separate Worktrees and branches from the freshly fetched Target Branch, and runs their implementation Agent Attempts concurrently. Agents check their work and commit locally; the Runner verifies their handoffs and owns all pushes, pull requests, CI monitoring, merges, and tracker mutations.

Every pull request in a Batch must become a CI-ready Pull Request before serial squash integration begins. Delivery requires both a confirmed merge and a ticket confirmed closed with the completed reason. After a successful Batch, the Runner performs Documentation Maintenance when at least one completed issue had the configured exact trigger label at delivery confirmation. It rescans for newly eligible children and explicitly closes the Parent Ticket only after a complete final scan permits it.

Execution failures enter an Operator Pause after any applicable automatic retry budget. The operator can retry, cancel the Run, or skip work within one issue or maintenance occurrence. Operator input never substitutes for a successful result. Agent-session state is in-memory for the current Run and each Run has a diagnostic JSONL log; a later Run resumes only exact persisted delivery evidence and never adopts or cleans up arbitrary earlier artifacts.

## User Stories

1. As an operator, I want to select a Project and Parent Ticket with one CLI invocation, so that I can deliver work across configured repositories without editing Runner code.
2. As an operator, I want invalid configuration, missing credentials, missing prompts, and malformed agent profiles rejected before workflow operations, so that a misconfigured Run does not begin delivery.
3. As an operator, I want an explicit Target Branch or the repository default, so that all delivery in a Run integrates into the intended branch.
4. As an operator, I want only same-repository direct children considered, so that delivery scope remains predictable.
5. As an operator, I want all hierarchy and dependency pages read successfully, so that incomplete discovery cannot be mistaken for completion.
6. As an operator, I want cross-repository children rejected explicitly, so that unsupported work is not silently omitted.
7. As an operator, I want open eligible children selected by issue number in Batches of at most the Project-configured maximum, so that selection is deterministic and concurrency is bounded.
8. As an operator, I want native blockers outside the Parent Ticket respected, so that dependencies are not bypassed by local scope.
9. As an operator, I want either completed or cancelled blockers to unblock dependent work, so that terminal decisions are respected.
10. As a developer, I want my assigned tickets skipped, so that the Runner does not take over externally owned work.
11. As an operator, I want complete and partial Reservations reported and skipped, so that a new Run does not take over earlier work.
12. As an operator, I want visible Reservations for selected tickets, so that concurrent human activity can recognize Runner ownership under the single-operator convention.
13. As an operator, I want Parent, ticket, and blocker state revalidated at operation boundaries, so that cancellation and scope changes prevent subsequent work.
14. As an operator, I want a cancelled Parent to stop its Run without child mutations, so that Parent cancellation does not rewrite child decisions.
15. As an operator, I want newly visible children included in later scans, so that the Run can continue through evolving delivery scope.
16. As an operator, I want a zero-child Parent to produce no work and stay open, so that absence of a breakdown is not treated as delivery.
17. As an operator, I want blocked, reserved, and externally owned open children identified in the final result, so that incomplete Runs leave an actionable explanation.
18. As a developer, I want isolated Worktrees, branches, and per-Attempt Git configuration, so that concurrent Agent Attempts do not contend on the same working tree or global Git configuration.
19. As an operator, I want a configurable agent, model, and native options for each attempt purpose, so that Project execution policy is explicit.
20. As a Project maintainer, I want editable Markdown prompts for implementation, CI repair, conflict repair, and documentation, so that repository-specific instructions remain caller-owned.
21. As an operator, I want agents restricted by their prompt contract to checks and local commits, so that deterministic Runner code owns delivery operations.
22. As an operator, I want structured Agent Attempt Results independently checked against Git, so that false commit claims and dirty Worktrees cannot enter ordinary publication.
23. As an operator, I want bounded same-session correction for malformed output, so that formatting errors can be corrected without silently accepting an invalid handoff.
24. As an operator, I want blocked and no-change delivery results reported without publication or completion credit, so that unresolved coding work remains visible.
25. As an operator, I want the Runner to publish one non-draft PR using the agent's title and body, so that PR metadata accompanies a verified change.
26. As an operator, I want only required CI checks to control readiness after a discovery delay, so that empty check sets and optional checks follow the agreed policy.
27. As an operator, I want fresh CI-repair Agent Attempts on the existing branch and PR, so that failures can be repaired without creating replacement delivery artifacts.
28. As an operator, I want every PR in a Batch ready before any merge starts, so that a partially ready Batch cannot begin integration.
29. As an operator, I want squash merges in PR creation order with the observed head SHA, so that integration order and the requested revision are explicit.
30. As an operator, I want an earlier queued merge confirmed before a later PR proceeds, so that a merge request is not mistaken for a completed merge.
31. As an operator, I want explicit merge conflicts repaired on the original branch and PR, so that the Runner can incorporate the current Target Branch without replacing ticket identity.
32. As an operator, I want CI and conflict repair budgets kept separate, so that one failure class does not consume the other class's allowance.
33. As an operator, I want one Project-wide Ticket Closure Policy, so that all PR-backed Delivery Tickets and Maintenance Tickets use consistent closure ownership.
34. As an operator, I want delivery counted only after a merged PR and confirmed completed closure, so that cancelled or merely merged work cannot inflate progress.
35. As an operator, I want already integrated work retained after a later Batch failure, so that recovery never rolls back successful deliveries.
36. As an operator, I want Documentation Maintenance after a successful Batch containing a completed issue with the configured trigger label, so that documentation catches up at an explicit delivery boundary.
37. As a Project maintainer, I want each documentation surface to own its Documentation Base, so that incremental review remains self-contained without a Runner-generated changed-ticket list.
38. As an operator, I want a standalone labelled Maintenance Ticket for each occurrence, so that documentation work remains visible without entering the Parent's delivery hierarchy.
39. As an operator, I want Documentation Maintenance to finish before the next Batch or Parent closeout, so that maintenance is a delivery barrier within the current Run.
40. As an operator, I want a valid clean no-change maintenance result to close its Maintenance Ticket directly, so that a successful review need not manufacture a commit or PR.
41. As an operator, I want transient external reads retried within fixed limits, so that temporary failures do not immediately require my input.
42. As an operator, I want safe set-like writes retried within fixed limits, so that temporary failures do not immediately require my input or duplicate resources.
43. As an operator, I want state-confirmed writes reconciled before the first attempt and after failures, so that an already-completed write is not replayed.
44. As an operator, I want resource-creating writes paused without automatic replay, so that I authorize retries that may create duplicates.
45. As an operator, I want to retry, cancel, or skip one issue after a failed operation while preserving verification and other issues.

## Implementation Decisions

### Authority and product boundary

- This specification synthesizes the completed [V1 planning map](https://github.com/xiakeng/sandcastle-runner/issues/1) and its five resolved decision tickets. The [final Run/configuration decision](https://github.com/xiakeng/sandcastle-runner/issues/6) supersedes earlier immediate-termination, retry-accounting, logging, and persistence proposals. The [Ticket Closure Policy amendment](https://github.com/xiakeng/sandcastle-runner/issues/4#issuecomment-5590682264) supersedes the original code-host-only closure rule.
- V1 is a local, single-Run CLI. Multiple Projects may be configured; one invocation selects one Project and Parent Ticket. Each attempt purpose selects one of the supported native Sandcastle agents (`codex`, `claude-code`, or `pi`), and Sandcastle runs without a sandbox. These are existing Sandcastle execution paths, not custom Runner integrations. OpenCode, Cursor, and Copilot are not supported; Runner documents that boundary but adds no dedicated rejected-agent allowlist or compatibility guard, so an unknown agent name still fails through ordinary configuration or execution error handling. Only GitHub Tracker and CodeHost adapters are implemented.
- Operators install, prepare, and authenticate the selected agent CLI and any skills, MCP servers, or native configuration its prompts expect. Runner does not install, migrate, or normalize those environments. It defines no universal agent CLI version floor and does not extend the documented native OS families into a broader support guarantee.
- The existing configured checkout is the Project's Git working location. The Runner owns dedicated branches and Worktrees. A temporary-clone deployment mode is not part of the resolved V1 contract.
- There is no Project lock, Parent Ticket lock, or cross-process coordination. The operating convention is one developer per Parent Ticket at a time; different Parent Tickets may be processed concurrently. Reservations are best-effort metadata, not atomic exclusion.

### CLI, configuration, and validation

- The CLI provides a `run` command requiring `--project` and exactly one of `--parent`, `--issue`, or `--document`; `--parent` takes a GitHub Parent Ticket number, `--issue` takes an optional issue number and otherwise uses the Project's configured `issueList`, and `--document` starts one fresh Project-scoped Documentation Maintenance occurrence without issue scope. Option order is flexible. Standalone Runs default to auto-merge; `--no-auto-merge` stops after the Pull Request is CI-ready, removes the Worktrees and local branches created by the current Run for that ticket along with its Agent logs, and preserves the remote branch, Pull Request, Reservation, and Recovery Snapshot. Explicit auto-merge flags are restricted to value-bearing `--issue` values.
- Each Project has one `config.yaml` configuration document, one always-required implementation Markdown prompt, enabled-only review and documentation prompts, and its own log directory. YAML comments are ignored by the loader. Prompt names and locations are fixed rather than configurable. The exact agreed layout and CLI spelling remain recorded in [decision #6](https://github.com/xiakeng/sandcastle-runner/issues/6#issuecomment-5592352688).
- Configuration includes `repository` in owner/repository form; absolute `checkout`; required `issueList` of unique positive safe issue numbers; optional `targetBranch`; `tracker.type`, `tracker.tokenEnv`, `tracker.runnerAccount`, and `tracker.reservationLabel`; `codeHost.type`, `codeHost.tokenEnv`, and `codeHost.adminMerge`; `workflow.review`, optional `workflow.maxReviewRounds`, and `workflow.docMaintainTriggerLabel`; `agents.implement`, `agents.ciRepair`, and `agents.conflictRepair`; conditionally required `agents.review` and `agents.documentation`; `timeouts.agentMinutes`, `timeouts.requiredChecksMinutes`, and `timeouts.mergeQueueMinutes`; required positive-safe-integer `maxBatchSize`; and `ticketClosure`.
- Every supplied profile for `implement`, `review`, `ciRepair`, `conflictRepair`, or `documentation` requires nonempty `agent` and `model` strings plus optional native `options`. Agent identity, model naming, and workflow purpose are distinct: the model never selects the agent, and each purpose selects its profile independently. Automatic and standalone `--document` Documentation Maintenance both use `agents.documentation`. Options are forwarded unchanged to the selected native factory; switching agents neither translates options nor promises they remain valid.
- Existing Codex-backed profiles migrate directly: add `agent: codex`, preserve `model` verbatim, and move the former `reasoningEffort` value verbatim into `options.effort`, including values such as `max`. Runner rejects the obsolete field, even beside new fields, and provides no default agent or model, automatic conversion, compatibility layer, or fallback that discards the old effort setting.
- `workflow.review` is a strict boolean and defaults to `true` when its field or the workflow object is omitted. `workflow.docMaintainTriggerLabel` is an optional string, trimmed at startup; an empty result disables automatic maintenance. The workflow object rejects unknown fields. Enabled review or documentation maintenance requires its profile and nonempty fixed prompt; startup errors identify both paths. Supplied profiles are still validated when their feature is disabled. Review uses `timeouts.agentMinutes`; it adds no timeout, fallback, compatibility mode, or migration.
- Both adapter types are `github` in V1. Omitting `targetBranch` selects the repository default; the Run then fixes that Target Branch. `ticketClosure` accepts only `runner` or `code_host`.
- Validate configuration, required prompts, credential references, and the Agent profile envelope before workflow operations. Missing selections and malformed options fail explicitly; no model substitution or option translation is permitted.
- `tokenEnv` references an environment variable read at startup and supplied only where needed by the adapter or subprocess. Secrets are not configuration values; missing credentials fail startup and there is no implicit dependency on interactive GitHub CLI authentication.
- `maxBatchSize` is required in every Project configuration and must be a positive safe integer. It caps selection for Parent and Standalone Runs; reservation-time validation can still produce a smaller Batch. Alternative configuration roots, dynamic prompt lookup, and schema migrations are excluded.

### Discovery, selection, and Reservations

- Read all pages of same-repository direct children and all native blocker information. Cross-repository children fail the Run; incomplete hierarchy or dependency reads never produce a partial selection or completion decision.
- An eligible Delivery Ticket is open, has no non-runner assignee, has no complete or partial Reservation, and has every native blocker closed. Blockers outside the Parent Ticket count; both `completed` and `not_planned` satisfy a blocker.
- Select eligible tickets by ascending issue number, reserving at most the configured `maxBatchSize` for a Batch. Log and skip external ownership and complete or partial Reservations.
- A Reservation combines the configured reservation label (the agreed marker is `sandcastle:reserved`) and the runner-account assignee. Partial writes are not compensated, repaired, or rolled back automatically. Their failures follow Operator Pause rules.
- Release Reservations on terminal Delivery Tickets or explicit release. Failed or interrupted work retains its Reservations for manual action; a new Run never takes over an unrecorded Reservation, while the same delivery scope can resume from its exact Recovery Snapshot evidence.
- Revalidate Parent Ticket, Delivery Ticket, and blockers at operation boundaries, not continuously during an active operation. Cancellation, external completion, removal from scope, or other terminal changes stop subsequent work; terminal tickets release their Reservations and the outcome is logged.
- A Parent changed to `not_planned` cancels the Run without modifying children. A Parent marked `completed` while a child remains open is contradictory and fails the Run.
- Rescan after every Batch and perform one final complete discovery scan before concluding exhaustion or closing the Parent Ticket. Children visible in those complete scans join the Run; children appearing after the final scan wait for another invocation.
- If no eligible work remains but open blocked, reserved, externally owned, or otherwise unresolved children remain, report `incomplete` and leave the Parent open. An initial complete scan with zero direct children returns `no_work` and leaves the Parent open. Once the Parent has had children, a final complete scan with every child closed permits Parent closure as `completed`, including all-cancelled children.

### Sandcastle execution and verified local handoffs

- Prepare a separate Runner-owned Worktree and branch from a freshly fetched Target Branch commit before initial implementation. Execute the selected Batch's implementations concurrently.
- Invoke Sandcastle with the Worktree as its working directory, the `head` branch strategy, the generic no-shell host executor, and one iteration. The initial probe uses a `SESSION_READY` completion signal; substantive execution has no completion-substring signal. Sandcastle owns agent invocation, streaming, timeout, and abort; the host executor owns the process handles it launches and OS-bound process-tree termination. Wait for both the Sandcastle result and an explicit host-settlement result.
- Every automatic follow-up waits for successful settlement of the preceding invocation. This gate covers initial-probe retries, retries after substantive invocation failure, missing-output continuation, structured-output correction, and the first substantive invocation after a completed probe. Failed or unconfirmed settlement produces a nonretryable Agent Attempt failure with the supplied cleanup evidence, session, Worktree, and diagnostic log, then enters Operator Pause without launching another process. Settlement covers owned direct children and observed descendants; it does not claim termination of arbitrary detached descendants, independently managed servers, or remote jobs.
- Caller cancellation is terminal for the current Agent Attempt. After owned-process settlement, it stops probe retries, execution retries, missing-output continuation, and structured-output correction without starting another invocation. Operator cancellation remains the existing `OperatorCancelled` outcome; failed settlement supersedes it with explicit cleanup evidence and manual handling.
- Substantive execution has one total deadline, established after session probing and retained across invocation retries, retry delays, missing-output continuation, and structured-output correction. Expiry settles owned processes, enters Operator Pause, and never automatically restarts the timed-out invocation or resets the deadline.
- An ordinary substantive Sandcastle invocation failure is handled generically, never by agent name, provider error text, `429`/network wording, or raw provider events. After successful settlement, Runner resumes the same probed session only when that session ID is usable, cancellation or timeout has not stopped the attempt, and the Agent Retry budget remains. Exhaustion enters Operator Pause; a missing or unusable session enters manual handling without a fresh-conversation fallback, transcript migration, or new durable conversation recovery. Authentication or configuration failures may consume this bounded budget before pausing. A schema-valid successful result proceeds through normal outcome and Git verification even when its output text contains an internal provider error; Runner does not inspect provider-specific raw events to invent another failure.
- Every concurrent Agent Attempt receives a unique `GIT_CONFIG_GLOBAL` file through its no-sandbox environment, isolating Sandcastle's Git identity and safe-directory writes from the user's shared global configuration.
- Supply optional Project instructions through `promptFile` and task context through `promptArgs`, and select the agent's native provider with its model and options. CI and conflict repairs use only `src/prompts/ci-repair-input.md` and `src/prompts/conflict-repair-input.md` plus the common Agent Attempt output protocol; they do not read Project repair prompts. Runner probes a `SESSION_READY` session with that same profile, then resumes it for the substantive attempt. Runner does not read `CODEX_HOME` or infer session roots from the operating-system home directory. Sandcastle's native default may use the selected agent's conventional storage. If it does not match actual storage, explicit native `options.sessionStorage` selects the lookup root: `hostSessionsDir` for Codex or Pi, and `hostProjectsDir` for Claude Code. That setting controls lookup and does not relocate the agent's storage; whether an override is needed depends on default/actual alignment, not solely the OS. Runner-owned templates under `src/prompts` identify the ticket, absolute Worktree, delivery branch, and freshly fetched Target Branch base. They also supply review handoffs, repair context, and output protocols. Project prompts contain repository-specific instructions and need no Runner-context placeholders.
- An Agent Attempt task identity is passed as the native Sandcastle run name. It identifies the task and purpose in log output but does not title the agent application's session list. Runner performs no Codex app-server initialization, `thread/name/set`, or naming-only dependency wiring. Guaranteed Runner-assigned application-session titles, automatic Codex directory discovery, and copyable manual resume commands are intentionally lost. Native run names do not affect session identity or continuation.
- Agents may work in their assigned Worktree, run appropriate checks, and commit locally. All Agent Attempt purposes, including repairs, leave push, PR operations, merge, closure, and other tracker mutations to Runner code. Without a sandbox this is an instruction/ownership contract, not an isolation guarantee.
- Ordinary Agent Attempt output contains exactly one `agent_attempt_result` tag with schema-validated JSON. Common fields are `outcome`, `summary`, `commits`, `checks`, and `blocker`; outcomes are `committed`, `no_change`, or `blocked`, with `blocker` required for `blocked`. Claimed commits contain SHA/message pairs. Checks record command, `passed`/`failed`/`not_run`, and details; claims are evidence rather than authority.
- Initial implementation results provide nonempty `pr_title` and `pr_body` for PR creation. Documentation `committed` results likewise require them; documentation `no_change` and `blocked` results do not. Repair uses the existing PR.
- Missing, malformed, or schema-invalid output uses the Agent Retry budget to resume the same session solely to re-emit a valid result, subject to the explicit settlement gate. Sandcastle's native structured-output retry loop is disabled in favor of this bounded Runner path, and a previously produced final payload is accepted only if it validates independently. Exhaustion or an unusable session enters Operator Pause. Native structured-output retries do not replace generic invocation-failure recovery.
- A `committed` result becomes a Verified Handoff only after successful explicit host-process settlement and independent confirmation of the expected Worktree, branch, recorded base, actual new commits, agreement with the claimed commit list, and a clean working tree. A false commit claim, missing commit, mismatched list, dirty Worktree, or other verification failure blocks ordinary publication and enters Operator Pause.
- When enabled, only a committed initial implementation Verified Handoff starts one fresh Review Agent Attempt on the same Worktree and delivery branch. `src/prompts/review-attempt-input.md` supplies the same six-field `REVIEW_INPUT` on initial and subsequent reviews: Worktree, delivery branch, Delivery Ticket reference, review base, implementation HEAD, and findings path. The reviewer reads the referenced issue and applicable repository instructions itself; Runner does not fetch or embed issue/specification bodies, standards, exceptions, or implementation-reported checks. Pull Request metadata remains in Runner state.
- Review invokes `code-review` for the supplied `reviewBase..implementationHead` diff and covers Standards and Spec without changing implementation files or creating commits. The reviewer writes actionable findings to a task/Run/round-specific Markdown file under the Project logs directory. Its strict `review_attempt_result` contains only `outcome` (`passed`, `findings`, or `blocked`) and the detail required by that outcome. Only `findings` adds `findings_file`, the exact assigned path; only `blocked` adds a nonempty `blocker` explanation for review Operator Pause. Passing requires both Standards and Spec to pass without a findings document. Findings, axis details, and relevant checks belong in the Markdown file rather than duplicated structured fields.
- Runner passes the findings path to the original implementation session, which reads it, fixes findings, runs relevant checks, and commits. Disputed or unfixable findings enter implementation Operator Pause. Runner resumes the original review session for the diff from the previous review HEAD to the latest fix HEAD, allowing surrounding-code reads, resolution checks, and findings introduced by the fix. `workflow.maxReviewRounds` is an optional positive integer with no default cap; the initial review counts as round 1. Execution retries and Operator Pause continuations do not consume another round. At the limit, the final findings still receive a fix before delivery continues without another review. Both sessions are reused within one Runner process; cross-process restoration is excluded. Structured-output correction, settlement, timeout, cancellation, and recovery retain common Agent Attempt behavior.
- After each completed review, Runner checks Worktree cleanliness and rejects reviewer-created commits. It does not compare frozen branch or merge-base values. Each implementation fix receives normal result/Git verification, and the final delivery evidence includes initial implementation and all fix commits, preserving the original Pull Request metadata. Findings and required session logs remain available throughout the loop. Successful completion and skip clean owned session logs and findings Markdown; pause/cancellation retain them under existing policy. Disabled Review bypasses the loop. No Review follows implementation `no_change`/`blocked`, Documentation Maintenance, CI repair, or conflict repair.
- A failed, timed-out, or aborted execution remains failed even if it left commits or output. Enter continues a usable Agent session; other text supplies recovery instructions. Without a usable session, including after a failed probe, Enter starts a fresh attempt and other text remains paused. Every subsequent result follows normal result and Git validation. These execution/handoff failures do not consume repair budget.
- An ordinary valid delivery `no_change` must explain the absent commit and pass clean-Worktree verification; it leaves the ticket unresolved for human judgment. A valid delivery `blocked` preserves its explanation and prevents publication. Neither counts as delivery; unresolved work produces `incomplete`.
- Operator input never creates a successful Agent result or bypasses result-schema or Verified Handoff validation.

### Pull requests, required checks, and serial integration

- The Runner pushes verified commits and creates one non-draft PR on the existing ticket branch with the AI-authored title and body unchanged. It does not synthesize metadata, require a closing keyword, deduplicate PRs, or recover a lost creation response.
- After PR creation or any repair push, wait a fixed 30 seconds before polling required checks. GitHub CLI required-check semantics govern readiness: empty or all-passing returned required checks produce a CI-ready Pull Request; pending checks continue waiting; terminal failure or cancellation starts CI repair. Optional checks do not add a readiness gate.
- Required-check waiting uses the Project-configured `timeouts.requiredChecksMinutes` limit. Timeout enters Operator Pause without consuming a repair attempt. Failed check reads use the external-read retry policy.
- CI repair starts a fresh Agent Attempt on the original branch and PR, supplying failing check names, states, and log links. Publish a Verified repair commit, then repeat discovery delay and required-check polling.
- All PRs in a Batch must be CI-ready before any is merged. If the barrier cannot be satisfied, none in that Batch is merged. After it is satisfied, integrate in ascending PR `createdAt`, breaking ties by PR number; later PRs never overtake earlier ones.
- Request squash merge only, supplying the observed PR head SHA. The Project may enable the merge command's admin bypass. The Runner does not inspect rulesets, classic branch protection, or review state, and does not proactively update a branch or rerun CI solely because the Target Branch advanced.
- A non-conflict merge rejection enters Operator Pause and preserves the original GitHub error. An explicit conflict reported by a merge request starts conflict repair; no speculative conflict-repair attempt is launched.
- Conflict repair uses a fresh Agent Attempt on the existing branch and PR, incorporates the current Target Branch, and commits the resolution. Independently verify and push, then repeat the same 30-second delay and required checks. CI failures after conflict repair use the CI budget.
- If GitHub queues the merge, wait for confirmed `merged=true` before advancing. The Project-configured `timeouts.mergeQueueMinutes` limit applies; failure/timeout enters Operator Pause.
- CI and conflict repair have independent two-attempt automatic budgets per ticket, also applied to Maintenance Tickets. Schema-valid `blocked` or `no_change` repair results consume an attempt, as does a Verified repair commit proceeding to publication. Agent process failure, timeout, malformed-output exhaustion, or invalid handoff enters Operator Pause without consuming an attempt. If failure remains after two consumed attempts, pause; empty-input retry starts a fresh two-attempt operation budget. Total operator-authorized attempts are unbounded.
- A partially integrated Batch is never rolled back. Already completed deliveries retain their completion evidence; unresolved original PRs, branches, and Reservations remain available for operator action. No maintenance begins from a Batch that has not ultimately completed successfully.

### Completion and Ticket Closure Policy

- A Completed Delivery Ticket requires both a confirmed merged PR and tracker state `closed/completed`. Release of a Reservation, an Agent claim, or merge confirmation alone is insufficient. `not_planned` is handled cancellation, not delivery credit.
- Under `runner`, after merge confirmation close the PR-backed ticket as `completed` and verify its state. Closure mutation failures enter Operator Pause.
- Under `code_host`, rely on the returned AI-authored PR body and the host's closure behavior without synthesizing or requiring linkage. After merge confirmation wait 10 seconds and read the ticket; if still open, wait another 30 seconds and read again. Missing `closed/completed` confirmation is a merged-but-not-completed execution failure and enters Operator Pause. Terminal `not_planned` may release a Reservation but cannot establish completion.
- Apply the same Project-wide policy to PR-backed Maintenance Tickets. Direct Parent closeout and no-PR maintenance closure are separate Runner-owned operations.

### Documentation Maintenance

- `workflow.docMaintainTriggerLabel` is trimmed, defaults to `""`, rejects non-string values, and matches issue label names exactly and case-sensitively. Empty configuration disables automatic maintenance. It is distinct from `maintenanceTicket.label`.
- Record labels from the tracker read that confirms each merged Delivery Ticket is `closed/completed`. Do not replace this evidence with later tracker label reads.
- Evaluate automatic maintenance only after a whole Batch completes successfully. Trigger one occurrence when any completed issue in that Batch has the configured label; multiple matches still produce one occurrence. Parent labels, delivery counts, Parent closeout, cancellations, failed Batches, and CI-ready unmerged Pull Requests do not trigger it.
- Each occurrence creates a new same-repository standalone Maintenance Ticket. Ensure the configured Maintenance Ticket label exists, then reuse the ordinary documentation attempt, publication, checks, CI/conflict repair, merge, and closure flow. A valid `no_change` closes the Maintenance Ticket without creating a Pull Request.
- Automatic Documentation Maintenance is an inter-Batch barrier. It must succeed before next-Batch discovery or Parent closure. Recovery resumes the same unfinished occurrence only while the current startup configuration still matches its stored delivery-time labels.
- If the current trigger is empty or no longer matches, stop automatic continuation without closing, deleting, or cleaning the existing Maintenance Ticket, Pull Request, branch, or Worktree, and report recorded artifact locations for manual handling.
- `--document` is mutually exclusive with `--parent` and `--issue`. It ignores `issueList`, requires the Documentation Maintenance prerequisites but not a trigger label, performs one complete Parent-independent occurrence, and exits. Every invocation starts fresh and does not read or write delivery Recovery Snapshot state.
- Prepare a fresh Worktree and branch from the latest Target Branch. Supply the ordinary Maintenance Ticket, Worktree, branch, and fresh base metadata to the editable documentation prompt. Each documentation surface owns its Documentation Base and advances it only after complete review.

### Recovery state, failure handling, and Operator Pause

- A delivery-scoped Run records its Recovery Snapshot as JSON, including publication identities, phase, Target Branch and remote-base facts, pending pushes, fresh repair Worktree/branch/head evidence, and independent CI/conflict repair budgets with consumed attempts and operator-authorized generations. Restart resumes only from exact persisted evidence; an interrupted push is adopted only when the remote head matches the recorded intended head, while unexpected advances pause without overwrite, rebase, or force-push. A `--document` Run reads and writes no delivery Recovery Snapshot.
- A recovered Batch retains its persisted size. A changed `maxBatchSize` affects only Batches discovered after recovery, never truncating or expanding already persisted delivery work.
- Recovery deliberately excludes old-process management, adoption of missing snapshots, and unrequested recovery state matrices. The audit log remains diagnostic only and is never recovery input.
- The phase flow covers discovery, reservation, Worktree preparation, implementation, publication, CI wait/repair, merge/conflict repair, completion verification, documentation maintenance, rescan, Parent closeout, and terminal outcome. Operator Pause is an execution event, not a resumable persisted phase.
- A Run never takes over Reservations, Worktrees, branches, commits, PRs, or Maintenance Tickets that are not part of its exact persisted evidence, and it never automatically removes ambiguous artifacts. Residual artifacts making children ineligible are reported as incomplete work; the operator must finish or remove them before a Run can own that work.
- ADR-0001 governs automatic retry: `operationRetry` and `agentRetry` are additional attempts after the initial attempt, and the configured delay arrays are seconds with the final delay reused. Failed external reads, including GitHub/API reads, remote Git queries, and fetch but excluding ordinary local Git/filesystem reads, use Operation Retry; each external command/API invocation has a fixed 60-second timeout. Agent-session probes also use Operation Retry. Exhaustion enters Operator Pause, and manual retry resets the automatic budget.
- Transient failures of safe set-like external workflow writes use Operation Retry and its delay schedule. State-confirmed writes reconcile their target state before the first attempt and after each failure; an already-achieved target is treated as success. Resource-creating writes, including Pull Request and Maintenance Ticket creation, receive no automatic replay. Other failed external or local workflow writes, including local Worktree operations, enter Operator Pause.
- Operator Pause gates new Agent steps, session probes, automatic retries and continuations, verification, publication, and integration across its Run. In-flight invocations and observations continue. Runner retains original outcomes and logs until all pending interventions resolve, then processes each outcome once under normal validation and retry rules. Prompts serialize by invocation identity, provider, native session when known, Worktree, diagnostics, and outcome. Resolving one entry cannot release another, and unrelated Runs remain independent. The same boundary applies to implementation, review and review fixes, CI/conflict repair, Documentation Maintenance, and publication recovery.
- An Operator Pause has no timeout. Exactly `q`, or EOF, cancels the Run after owned-process settlement. Failed settlement remains visible. Unsupported input explains the supported actions and stays paused without changing workflow state or resetting a retry budget.
- Operator Pause diagnostics identify the invocation, selected agent, session ID, working directory, and diagnostic log path, showing `unavailable` for missing values and only the Runner actions permitted by the current state. The log path is shown even when a session ID exists. Runner prints no copyable manual resume command; manual recovery uses the selected agent's own recovery interface with the displayed evidence.
- Enter retries a failed read or write directly, resetting its applicable automatic budget. Creation retries may duplicate PRs, issues, or comments. Label/assignee changes and push retry the original action. Worktree creation retries the original command after the operator repairs partial state. Add no deduplication or push/Worktree existence checks.
- Merge-request retries refresh the PR status and HEAD: merged proceeds to closure, accepted/queued waits, otherwise request merge. Merge-wait recovery uses the same decision. Check timeouts refresh checks: ready proceeds, failure enters repair, pending opens another wait window. Exhausted repair budgets refresh current checks or conflict evidence before opening a fresh two-attempt budget. Failed observations retry only the observation.
- Agent pauses accept `s` to skip the current issue or maintenance occurrence. Enter sends `continue` in a usable session; other text, including JSON, supplies recovery instructions. Without a usable session, Enter starts a fresh attempt and other text remains paused. Automatic recovery remains bounded by Agent Retry, with process settlement required before another invocation.
- Non-Agent pauses within a selected issue offer Enter to retry, `s` to skip, and `q`/EOF to cancel. Scope begins at reservation and includes issue-specific Parent/child reads, publication, repair, merge, closure, and cleanup. Discovery, startup, Batch-shared fetch, and final Parent closure offer no skip. Maintenance preparation offers occurrence-level skip before an issue exists.
- Skip preserves existing side effects and prevents reselection during this Run while other issues continue. Before publication, attempt Reservation release; another `s` can abandon release with possible residue reported. After delivery, keep delivery completed and leave unfinished cleanup/release pending. Skipped work and unfinished cleanup return `incomplete`; report known artifacts and uncertain writes, including unknown creations.
- Closure retries observe current state before closing or waiting under the configured policy. Recovery inconsistencies rerun the current checks. Cleanup retries remaining work with ownership validation; success requires actual completion. Historical accepted-residual recovery records remain unchanged.
- Startup validation errors, missing credentials/prompts, unsupported cross-repository children, contradictory terminal Parent state, and ordinary business outcomes bypass Operator Pause.
- Agent Attempt, required-check, and merge-queue timeouts are required positive Project configuration. The checked-in template uses 120, 60, and 60 minutes respectively. The 60-second external-call timeout, 30-second check-discovery delay, and code-host closure reads after 10 and another 30 seconds are fixed; read and write retry delays come from the Project Retry Policy.

### Audit and terminal outcomes

- Each Run creates a JSONL file under its Project's log directory, named with UTC timestamp, Parent number, and Run UUID. Workflow operations append separate start, result, and error events.
- Every event contains `timestamp`, `runId`, `project`, `parentTicket`, `phase`, `operation`, `target`, `attempt`, `result`, and `error`, with optional scoped Agent Attempt IDs, diagnostic-log paths, transitions, and sanitized diagnostics. Exclude tokens, credential values, raw operator input, and raw Agent streams from all event data. Record pause actions without copying operator input.
- Audit creation/append failures permit only Enter to retry the same log action and `q`/EOF to cancel. All other input, including `s`, remains paused. Never replay a completed business action because its audit append failed. An uncertain append may produce duplicate diagnostic records. Logs never reconstruct state.
- Terminal outcomes are `succeeded` for all owned work completed; `no_work` for an initial complete scan with no children; `incomplete` for remaining blocked/reserved/externally owned or valid blocked/no-change delivery work; `cancelled` for Parent cancellation or operator abort; and `failed` for invalid startup, unsupported/contradictory states, or other unrecoverable errors.
- `succeeded` and `no_work` return exit code zero. Other outcomes return nonzero. The final operator report shows every processed Delivery and Maintenance Ticket in processing order, then remaining discovery reasons, Retained Worktrees, and the Audit Log path. The structured `CliResult` remains available to callers. Closing execution resources must respect Sandcastle's supported lifecycle and must not become automatic deletion/adoption of earlier artifacts.

### Orchestration boundaries

- Keep the Run orchestration deterministic behind six agreed boundaries, rather than distributing scheduling decisions across prompts.
- `Tracker` owns Parent/child/dependency/state/closure-reason/assignee/label/Reservation reads and tracker mutations, including maintenance creation and closure.
- `CodeHost` owns repository and PR reads, required-check evidence, mergeability, queues, PR creation, merge requests, and merge confirmation.
- `GitWorkspace` owns Target Branch fetches, Runner-owned Worktree creation/inspection/closure, commit and working-tree verification, and branch pushes.
- `AgentExecutor` owns Sandcastle-backed execution with prompt, Worktree, selected agent, model, native options, environment, timeout, resulting output/failure, and the gate that waits for explicit owned-process settlement before any automatic follow-up. It is the production process boundary.
- `Clock` supplies time, delays, and timeouts. `OperatorIO` displays pauses and returns operator input.
- Tracker selection and hosting selection stay separate for future adapters. No dynamic adapter/plugin loading is introduced. Configuration and logs use the real filesystem, including temporary directories in tests, without another filesystem abstraction.

## Testing Decisions

- Reuse the testing boundaries already agreed in [decision #6](https://github.com/xiakeng/sandcastle-runner/issues/6#issuecomment-5592352688): the main test entry is a complete Run driven by scripted fakes for Tracker, CodeHost, GitWorkspace, AgentExecutor, Clock, and OperatorIO. This is one high-level orchestration seam backed by the six necessary external boundaries, not a separate mock surface for every function.
- Good tests observe selections, externally visible operation order and effects, publication/merge barriers, completion evidence, operator interactions, summaries, and exit status. Do not assert private helper structure or mirror the implementation. Control concurrent completions and time explicitly rather than relying on real sleeps.
- Routine tests launch no real authenticated agent sessions and mutate no live GitHub, Plane, or remote repository. Configuration and logging tests use temporary real directories. Focused Git integration tests, when included, use temporary local repositories for Worktree/base/commit/dirty-state verification. Do not add a production filesystem port solely for tests.
- Use the host-executor boundary to verify that pending or failed settlement prevents the next automatic probe, task, continuation, or correction. Keep real harmless-child Sandcastle lifecycle tests against temporary local Git repositories for direct-child and supported owned-descendant cleanup, and report tests skipped by host platform rather than treating a fake run rejection as lifecycle evidence.
- Native-factory and scripted-protocol assertions establish the tested contracts only. Real local-process tests establish the measured lifecycle cases only. Together they do not prove live authenticated compatibility for Codex, Claude Code, or Pi, behavior on every OS, or cleanup of arbitrary detached descendants, independently managed servers, or remote jobs.
- Verify cancellation during probing, substantive execution, retry backoff, missing-output recovery, and structured-output correction prevents another invocation and remains cancellation. Verify the one substantive deadline expires during execution and output recovery, with process settlement before Operator Pause and no automatic restart.
- Cover every defined phase transition, conditional branch, retry boundary, Operator Pause action, cleanup path, and terminal outcome with at least one focused deterministic scenario. Organize tests around behavioral cases rather than one test per function or numerical coverage targets.
- The scenario matrix includes configuration and credential validation, including `maxBatchSize` rejection and a non-default Batch size; Agent Profile validation, native option preservation, direct migration, and `reasoningEffort` rejection; Project/prompt resolution; pagination and incomplete reads; unsupported hierarchy; blocker scope/order/closure; external ownership; complete/partial Reservations and write failure; boundary revalidation and cancellation; newly added/removed children; initial zero-child and all-terminal Parents; residual artifact rejection; Worktree preparation; per-Attempt Git configuration; every Agent result, output correction, verification failure, and timeout; publication; required-check discovery/empty/pending/failure/cancellation/timeout; independent repair budgets and resets; ordered merge, queue, rejection, conflict, and partial integration; both closure policies; label-triggered automatic maintenance, explicit invocation, no-change closure, barrier, recovery reevaluation, and abandonment; log failures and omissions; and every Operator Pause input branch including EOF, unsupported input, issue/maintenance skip, and rejected success/gap payloads.
- Verify recovery boundaries explicitly: a Run resumes only exact persisted delivery evidence, does not adopt ambiguous prior Reservations, Worktrees, branches, PRs, or Maintenance Tickets, does not reconstruct the documentation counter, and never reads an audit log or in-memory agent-session state as recovery input.
- The first complete success scenario configures `maxBatchSize` to 3 and has five Delivery Tickets: tickets 1–4 are mutually unblocked; ticket 5 depends on all four. All operations succeed on the first attempt. Assert Batch(1, 2, 3), Documentation Maintenance, Batch(4), Batch(5), final Documentation Maintenance, and completed Parent, in that order.
- A second complete scenario uses the same topology and ultimately succeeds while exercising: external read success on call five; failed write then empty-input retry; Agent process failure followed by bounded same-session recovery or Operator Pause; invalid structured output corrected in its original session; invalid Verified Handoff followed by recovery without accepting the false claim; unsupported text followed by a verified retry; CI repair; retried required-check reads; conflict repair; maintenance CI and merge repair; and every delivery and Parent confirmed completed.
- Keep incompatible failure outcomes in focused scenarios instead of forcing them into the successful recovery scenario: `q`/EOF, permanently exhausted reads awaiting input, repeated unsupported input, valid `blocked`/`no_change`, unsupported children, contradictory Parent state, residual Reservations, and startup failures.
- Prior art is planning evidence, not an existing production suite: the [handoff prototype at the recorded commit](https://github.com/xiakeng/sandcastle-runner/commit/e85e7cb759d2a87a39424caf1d9c05b7281731d9) demonstrates committed, no-change, false-claim, output-correction, and process-failure decisions as a static model. The repository's [Sandcastle feasibility research](https://github.com/xiakeng/sandcastle-runner/blob/main/docs/research/sandcastle-feasibility.md) records execution-boundary evidence. No live authenticated agent or end-to-end Sandcastle execution was established by the prototype; fake acceptance tests must not be reported as such validation.

## Out of Scope

- Plane Community adapter implementation, support or compatibility paths for OpenCode, Cursor, or Copilot, sandbox/container execution, stronger OS-specific process supervision, a daemon, web UI, or remote control plane.
- Durable agent-conversation state, cross-Run agent-session adoption, transcript migration, databases, event-sourced workflow storage, automatic reconciliation/deduplication/cleanup of ambiguous prior artifacts, and cross-Run documentation scheduling credit.
- Project/Parent locks, atomic Reservations, multi-host coordination, recursive child scope, cross-repository child delivery, or bypassing native blockers to keep a Run busy.
- Dynamic adapter/plugin loading, alternate configuration roots, configurable prompt names, or schema-version migration.
- PR metadata synthesis, closing-keyword validation, lost-create-response recovery, automatic rollback of integrated work, proactive Target Branch updates solely due to branch advancement, and separate review/ruleset/protection inspection.
- Routine test execution against live authenticated agents, GitHub, Plane, or remote repositories.
- Implementation-ticket breakdown, application implementation, and production rollout as part of this specification-writing task. These follow this implementation-ready contract.
