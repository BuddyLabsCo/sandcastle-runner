# Claude Code and OpenCode agent-session feasibility

Status: research and adapter-level inspection; no provider implementation or authenticated end-to-end agent run.
Checked: 2026-09-29. Tracking: [issue #176](https://github.com/BuddyLabsCo/sandcastle-runner/issues/176).
Runner baseline: `51cb13d6045d150b9fb9cb8bb8540e76c38502e3`.
Dependency inspected: `@ai-hero/sandcastle@0.12.0`, npm `gitHead` `e99f832f26dc9d245c019a9ddd19fa5dee792427`.

## Decision

**Both providers are feasible, but neither is a configuration-only change. Claude Code is the smaller first integration. OpenCode requires closing a concrete gap in the pinned Sandcastle provider or using its native API behind the existing executor boundary.** This is an engineering assessment from the current code and the primary-source findings below, not demonstrated runtime parity.

Keep the existing orchestration and verified-handoff rules. First support the five current attempt purposes: implementation, review, CI repair, conflict repair, and documentation maintenance. Session browsing, forking, usage dashboards, live event reconnection, and cross-provider transcript migration are not current Runner features and need not be added to deliver provider parity. [Executor contract](../../src/run/contracts.ts), [attempt entry points](../../src/run/attempt.ts), [review entry point](../../src/run/review-attempt.ts)

## The pinned dependency is the deciding constraint

Sandcastle already exports `claudeCode()` and `opencode()`. Claude Code supplies session storage, stdin prompt delivery, `--resume`, and effort options. OpenCode emits a captured ID from `step_start`, but has no `sessionStorage` and its command builder ignores `resumeSession`. Sandcastle rejects resumed runs without a session-storage implementation before launching the agent. Therefore changing only `codex(...)` to `opencode(...)` would allow a probe to return an ID but fail before the resumed substantive task. [Provider source](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts), [resume precheck](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/resumePrecheck.ts)

A local, credential-free check instantiated both installed providers, supplied a dummy resume ID, and inspected the generated command and parsed synthetic session event:

| Check | Claude Code | OpenCode |
| --- | --- | --- |
| `sessionStorage` exists | Yes | No |
| Generated command includes supplied resume ID | Yes (`--resume`) | No |
| Synthetic native session event produces session ID | Yes | Yes |
| Prompt transport | stdin | positional argument |

This checks library behavior only. It did not launch either CLI or verify authentication, actual session persistence, output quality, CLI flag compatibility, or cancellation. The OpenCode positional prompt also deserves a long-prompt and Windows quoting check before adoption. [Installed package source](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts), [Runner command parser](../../src/adapters/no-shell-sandbox.ts)

## Native provider capabilities

Research date: 2026-09-29. This is documentation and published-source research, not a live-agent compatibility test. It describes native capabilities; the runner's pinned Sandcastle adapter can expose a smaller subset.

The primary sources establish that both providers can support persistent, programmable agent sessions. That does **not** establish complete compatibility with an existing Codex workflow: session ownership, configuration discovery, event meanings, approval policy, and restart behavior require provider-specific integration. Claude offers its Agent SDK and headless CLI; OpenCode offers a server, generated SDK, and headless CLI. [Claude overview](https://code.claude.com/docs/en/agent-sdk/overview), [OpenCode server](https://opencode.ai/docs/server/)

### Capability matrix

“Available” means a documented native surface exists, not that Sandcastle or this runner currently implements it.

| Capability | Claude Code / Agent SDK | OpenCode |
| --- | --- | --- |
| Headless launch | `query()` or `claude -p` | `opencode run`; persistent `opencode serve` |
| Stable identity and continuation | `session_id`, explicit `resume`, conversation fork | Session ID; CLI `--session`; HTTP prompt against existing ID |
| List/history/name | Current SDK `listSessions`, `getSessionMessages`, `renameSession`, creation `title` | Session list/messages/update APIs; creation title and PATCH title |
| Streaming/status | Typed SDK messages, optional partial output, result/error messages | SSE, message parts, session status, async prompts |
| Interrupt/stop | Streaming query interrupt; process termination is separate | Session abort; server lifetime is separate |
| Structured result | JSON Schema output and terminal validation errors | JSON Schema output, bounded retries and structured-output errors |
| Approvals/questions | `canUseTool`, permission modes, `AskUserQuestion` | Permission rules and permission/question request/reply endpoints |
| Model/reasoning | Model plus supported effort/thinking controls | Provider/model plus provider-specific variants/options |
| Worktree execution | Explicit `cwd`; native CLI worktrees | Explicit directory; existing Git worktrees; experimental worktree APIs |
| Cost/tokens | Result estimates and per-model usage | Assistant-message cost/token fields |
| Hooks/subagents | Hooks and autonomous subagents | Plugins/events/tool hooks and autonomous child agents |
| Crash/external-session parity | Conditional; persisted history is not a live-process handle | Conditional; discoverable backend and persisted data are different concerns |

Matrix sources: [Claude CLI](https://code.claude.com/docs/en/cli-reference), [published Claude SDK 0.3.284 declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.284.tgz), [Claude streaming input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode), [Claude structured output](https://code.claude.com/docs/en/agent-sdk/structured-outputs), [OpenCode CLI](https://opencode.ai/docs/cli/), [OpenCode SDK](https://opencode.ai/docs/sdk/), [pinned OpenCode SDK methods](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/sdk/js/src/v2/gen/sdk.gen.ts), [Claude hooks](https://code.claude.com/docs/en/agent-sdk/hooks), [OpenCode plugins](https://opencode.ai/docs/plugins/).

### Session ownership, naming, and recovery

Claude persists conversation transcripts and exposes IDs in initialization/result messages. Explicit `resume` selects one session; directory-based `continue` selects the latest and is inappropriate for concurrent sessions. Forking copies conversation history, not the filesystem. Cross-host recovery requires moving/persisting session data, not merely storing its ID. The experimental TypeScript V2 session API was removed in 0.3.142: build against `query()` and its session options. [Claude sessions](https://code.claude.com/docs/en/agent-sdk/sessions)

The published 0.3.284 TypeScript declarations expose `listSessions`, `getSessionMessages`, `getSessionInfo`, `forkSession`, and `renameSession`. Listing can span projects/worktrees and include programmatic sessions. `title` names a new session; persisted titles win on resume, so use `renameSession` for an existing one. Its documented implementation appends a custom-title record. These APIs provide a supported alternative to writing provider transcripts directly; verify their minimum supported version before adopting them. [Versioned SDK package](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.284.tgz)

Claude CLI additionally documents `--name`, `/rename`, and ID/name-based resume. It now has background-session commands including attach, stop, logs, and respawn. Those commands concern the background-session system; they do not establish that an arbitrary interactive CLI process can be attached through `query()`. The SDK's startup types explicitly include `session_held_by_background`. Treat persisted-session continuation and live-process attachment as separate features. [CLI reference](https://code.claude.com/docs/en/cli-reference), [SDK declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.284.tgz)

OpenCode's native CLI supports `run --session`, continuation/forking, `--title`, JSON event output, and attaching to an existing server. It also documents JSON session listing, export/import, and database-location commands. Therefore an adapter that rejects resume does not prove native OpenCode lacks resumable sessions. [OpenCode CLI](https://opencode.ai/docs/cli/)

The HTTP API provides create/get/list/delete, message history, title update, fork-at-message, abort, and status. The TUI is a client of a backend; another client can connect if its address is known. Starting `serve` separately creates another server, not a connection to the currently running TUI backend. Session access must account for the configured directory, data store, and backend ownership. Do not equate “same session ID” with “same running operation.” [Server API](https://opencode.ai/docs/server/)

### Events, stopping, and fault semantics

Claude streaming input supports queued prompts, interruptions, and permission interaction; single-message mode lacks the same interactive controls. Partial streaming output is opt-in. A result ends a turn; that does not itself imply the persistent process should be killed. `interrupt()` controls the active query, whereas `close()` terminates the process and associated transports. [Input modes](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode), [Streaming output](https://code.claude.com/docs/en/agent-sdk/streaming-output), [SDK declarations](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.284.tgz)

For OpenCode, the pinned SSE implementation registers a live listener and emits connection/heartbeat events; the SSE envelope has no `id`. The generated client has reconnection/backoff and Last-Event-ID machinery, but this endpoint does not establish durable event replay. **Inference:** after reconnect, refetch messages and pending requests instead of treating the stream as an exactly-once log. The inspected status implementation stores active status in an instance-local map and returns idle for absent entries; idle alone cannot prove that a pre-crash task succeeded. [Pinned event handler](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts), [SSE client](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/sdk/js/src/v2/gen/core/serverSentEvents.gen.ts), [Status implementation](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/opencode/src/session/status.ts)

Research does not establish exactly-once tool execution, automatic in-flight tool recovery, or safe concurrent writers for either provider. Proof tests must distinguish client disconnect, runner death, agent/backend death, and cancellation while a tool has already changed files.

### Structured output, approvals, and settings

Claude supports a JSON Schema output format and a structured result with explicit failure handling. OpenCode documents schema validation/retries, but its current SDK page is internally inconsistent: examples use `format` and `structured_output`, while a method table says `outputFormat`. The pinned generated types instead expose `format` and `AssistantMessage.structured`. Pin the server/client version and validate against its generated contract; do not copy these examples interchangeably. [Claude structured output](https://code.claude.com/docs/en/agent-sdk/structured-outputs), [OpenCode SDK documentation](https://opencode.ai/docs/sdk/), [Pinned generated types](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/sdk/js/src/v2/gen/types.gen.ts)

Claude's `canUseTool` handles approvals and `AskUserQuestion`, pausing until a response; earlier permission rules can bypass that callback. PreToolUse hooks are the appropriate interception point for logic that must examine every tool call. OpenCode has allow/ask/deny rules, plus separate pending-question and permission reply endpoints. **Integration implication:** unattended execution must deliberately choose an approval policy; leaving requests unanswered is not compatible automation. [Claude user input](https://code.claude.com/docs/en/agent-sdk/user-input), [OpenCode permissions](https://opencode.ai/docs/permissions/), [Question API](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/opencode/src/server/routes/instance/httpapi/groups/question.ts), [Permission API](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/opencode/src/server/routes/instance/httpapi/groups/permission.ts)

Model settings require translation, not a shared unvalidated effort string: Claude effort levels depend on the model; OpenCode variants and reasoning options depend on its selected provider/model. Run either agent in the runner-owned checkout/worktree. Claude's native worktree flag is optional; OpenCode exposes experimental worktree methods, but an integration can use an existing directory without adopting them. [Claude CLI](https://code.claude.com/docs/en/cli-reference), [OpenCode models](https://opencode.ai/docs/models/), [OpenCode generated methods](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/sdk/js/src/v2/gen/sdk.gen.ts)

### Instructions, skills, MCP, and delegation

Claude's newest CLI can read AGENTS.md directly (v2.1.277+), but by default a project/ancestor CLAUDE.md or CLAUDE.local.md suppresses that fallback. Some configurations require v2.1.281+. A CLAUDE.md containing `@AGENTS.md` remains a documented compatibility path. Do not assume the installed binary behaves like today's docs. [Claude project memory](https://code.claude.com/docs/en/memory)

Explicitly select SDK `settingSources` and verify discovery. Current documentation says omission loads user/project/local settings; host-managed settings and some global inputs remain separate. Claude skills live under its filesystem conventions, and tool access still controls whether skills can execute. OpenCode loads AGENTS.md, supports CLAUDE.md fallbacks, and discovers `.opencode/skills`, `.claude/skills`, and `.agents/skills` at documented project/global locations. This does not promise discovery of Codex plugin-cache paths. [Claude feature loading](https://code.claude.com/docs/en/agent-sdk/claude-code-features), [OpenCode rules](https://opencode.ai/docs/rules/), [OpenCode skills](https://opencode.ai/docs/skills/)

MCP exists in both: Claude SDK `mcpServers` and OpenCode's `mcp` configuration support external tools. Tool registrations, credentials, permission configuration, and plugin paths must be provisioned in each runtime; Codex-installed connectors do not automatically become another provider's tools. This portability conclusion follows from their separate configuration surfaces. [Claude MCP](https://code.claude.com/docs/en/agent-sdk/mcp), [OpenCode MCP](https://opencode.ai/docs/mcp-servers/)

Both support autonomous delegation. Claude documents nested subagents and depth/concurrency/spend limits; OpenCode supports automatically selected subagents with child sessions and task permissions. Hooks/plugins can observe tool/session events. Nevertheless, loading `/tdd` or `/code-review` text does not translate Codex-specific collaboration tool names, context-free handoffs, waiting semantics, or required parallel review axes. Those workflows need semantic acceptance tests, including that both reviewers actually ran. [Claude subagents](https://code.claude.com/docs/en/agent-sdk/subagents), [OpenCode agents](https://opencode.ai/docs/agents/), [Claude hooks](https://code.claude.com/docs/en/agent-sdk/hooks), [OpenCode plugins](https://opencode.ai/docs/plugins/)

### Usage, authentication, and deployment boundaries

Claude exposes token/model usage and estimated cost; current resumed-session totals can include earlier spend, so summing results can double-count. Result `usage` excludes subagents, whereas `modelUsage` includes them. Cost estimates are not authoritative billing. OpenCode assistant messages carry cost and input/output/reasoning/cache token fields; do not infer identical accounting scope across providers. [Claude cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking), [OpenCode message types](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/packages/sdk/js/src/v2/gen/types.gen.ts)

Claude Agent SDK runs a binary in infrastructure the integrator operates; hosting needs executable tools, filesystem, credentials, and suitable isolation. Anthropic states third-party products may not offer claude.ai login/rate limits without prior approval, and SDK usage is governed by its Commercial Terms. Consequently, a user's successful personal CLI login is not sufficient evidence for a distributable third-party product's authentication design. [Hosting](https://code.claude.com/docs/en/agent-sdk/hosting), [SDK overview and terms](https://code.claude.com/docs/en/agent-sdk/overview), [Quickstart authentication](https://code.claude.com/docs/en/agent-sdk/quickstart)

OpenCode's inspected repository uses the MIT license; that software license does not grant access to model-provider accounts or override their terms. Credentials may come from its auth store or environment. Its server supports configured HTTP Basic authentication, with loopback the documented default host. Shared/remote operation therefore needs deliberate server ownership and access configuration. [Pinned license](https://github.com/anomalyco/opencode/blob/7945de208964a49300d7f770d1a71d078db9a4c4/LICENSE), [CLI authentication](https://opencode.ai/docs/cli/), [Server authentication](https://opencode.ai/docs/server/)


## Recommended integration scope

The following is a proposal, not an approved implementation spec.

1. **Add provider identity to the existing per-purpose agent profile.** Use `codex`, `claude-code`, or `opencode`, defaulting omitted values to Codex for existing configurations. Carry the selected identity through both `execute` and `executeReview`, including repair and maintenance calls. Keep selection local to the existing executor boundary; a plugin registry or new orchestration framework is unnecessary. Model and effort/variant validation must be provider-specific, with no silent model substitution or effort downgrade. Configuration syntax is a design choice to settle in implementation; arbitrary Codex effort strings cannot be assumed equivalent elsewhere. [Current configuration](../../src/config.ts), [executor inputs](../../src/run/contracts.ts)
2. **Deliver Claude Code first through Sandcastle.** Reuse `claudeCode()` and the current output validation/retry flow. Add provider-specific naming, diagnostics, resume hints, and process-error classification. To preserve the exact post-probe rename boundary, the documented `renameSession` API is a candidate; evaluate its additional SDK dependency against using the CLI's creation-time name flag. Naming at creation would preserve the visible outcome but change the existing timing contract and therefore needs an explicit implementation decision. Keep warning-only rename failure and reuse the established ID. Do not manually edit transcript files.
3. **Close OpenCode resume support before enabling it.** Prefer a verified upstream Sandcastle update or a focused change that supports native session existence/resume and does not invent JSONL session files. Adding `--session` alone is insufficient because Sandcastle's resume precheck also requires storage support. If accommodating OpenCode's native storage would force a misleading implementation of that interface, use a small OpenCode HTTP/SDK executor behind `AgentExecutor`, retaining shared result validation and retry policy. Its create/update/prompt/abort endpoints fit this task, but introduce server startup, authentication, lifecycle, and event reconciliation work. Do not introduce a long-running server just to avoid evaluating the narrower CLI route. [Pinned resume precheck](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/resumePrecheck.ts), [OpenCode server](https://opencode.ai/docs/server/)
4. **Treat configuration and tooling as part of parity.** Install or expose the actual required skills, make instruction loading explicit, and configure each provider's MCP endpoints and credentials. Preserve the existing intent of `disableWebSearch`: disable the built-in web-search tool while leaving unrelated MCP configuration alone; do not claim it disables all network access. Apply the selected provider's rule to initial and resumed sessions. Keep model and provider identity fixed during an attempt's continuations. Documentation must describe provider prerequisites instead of promising that existing Codex login/config works everywhere.
5. **Do not expand scope to a session platform.** Preserve the five attempt types, tagged results, verified Git handoffs, operator pauses, and Runner-owned publication. Listing/history/forking/token dashboards and automatic cross-provider fallback can remain out of scope. A Codex conversation cannot be resumed by passing its ID to Claude Code or OpenCode. Durable provider-session recovery would require persisting provider, ID, cwd, model/settings, and a reconciliation boundary; it is a separate feature from the present workflow snapshots.

Expected relative effort: Claude Code is a bounded adapter/configuration change with meaningful naming/tooling validation; OpenCode is a larger integration because current dependency resume support is missing. No calendar estimate is defensible before the focused probes below.

## Acceptance probes before claiming support

Use temporary repositories and disposable sessions. The current research ran only the provider-construction/parser check described above; all live probes below remain pending.

| Probe | Required evidence |
| --- | --- |
| Preparation, naming, and continuation | Probe returns ID; deterministic title is visible through supported readback; substantive task and subsequent continuation retain the ID; rename failure does not duplicate a session. Exercise all five operation names with distinct issue/PR numbers. |
| Handoff and review protocol | Both result schemas pass through the existing validation path; missing, duplicate, malformed, and schema-invalid tags produce the configured same-session correction or pause. Native structured JSON must not bypass Runner's commit/branch/dirty-state checks. |
| Failure and operator recovery | A recoverable process failure continues the correct session with the bounded delay/budget. Auth/config/permission failures are visible rather than an endless retry. Nonempty operator instructions target that same session. |
| Timeout and cancellation | Cancel during model execution and during a child tool process; observe child-process termination, no later writes, and no concurrent old/new writer on retry. Test deadline expiry during retry delay as well. Existing fake signal tests are insufficient for this claim. |
| Environment and concurrency | Two temporary worktrees preserve distinct cwd, branch, log/session mapping, Git config, and selected provider. No wrong-project resume. Validate large prompts, paths with spaces, and supported Windows launcher behavior. |
| Settings and tooling | Model/effort/variant is honored or rejected explicitly. Built-in web search is denied when requested and otherwise keeps configured defaults. Required instructions, `/tdd`, `/code-review`, delegation, and MCP tools are actually usable under each provider. |
| Recovery boundary | Restart Runner and establish whether it resumes only workflow state or the provider session. Missing/stale provider sessions fail visibly. If durable session recovery is added later, test interrupted writes and distinguish new turns from replay of partially completed tool actions. |
| OpenCode native/dependency contract | Verify the selected CLI's flags, session lookup/resume, title update, prompt transport, tool policy, and event fields against the exact supported version. If using HTTP, prove server ownership/shutdown and reconcile authoritative messages/status after stream loss rather than relying on replay. |

Then parameterize focused existing adapter/operation tests across supported providers, run `npm run verify`, and perform a disposable end-to-end handoff for each new provider. Tests that invoke real agents should remain separate from the default credential-free suite. ## Research limits

This note inventories source behavior and current documented APIs; it does not certify a minimum supported CLI/SDK version or actual model entitlement. No live Claude Code/OpenCode task, user-session rename, paid model request, provider installation, or runtime provider change was performed. Provider docs change independently of the pinned Sandcastle package; recheck exact versions when implementation starts. Existing recovery/spec documentation has historical statements that should not override inspected executable behavior.
